# Recovery status — local candidate, release blocked

The live authoritative source for accepted R17+ results is each DayRegistry's SQLite `events` journal. Its full private snapshots include claims, strikes, replay responses, identity/recovery hash and streak dates. D1 `r17_files` is a delayed mirror; `r17_players` and legacy tables supplement identity. Catalog ordinals, score assets, config and the existing daily commitment metadata are required to interpret a restored file. `r17_boards` is a derived closed snapshot.

`scripts/backup-production.sh` exports D1 only. No new production backup was performed: there is no releasable candidate. Existing rollback application IDs were captured read-only. A D1 export cannot recover acknowledged events not yet mirrored. The local tests prove process restart/replay with intact journal storage, failed sync rejection, outage/partial-mirror recovery, concurrent revisions and original file recovery. They do **not** prove survival after loss of the journal storage itself, a private hosted backup restore, or a complete DR RTO/RPO. Those measurements are unavailable, not zero.

The new mirror checkpoint is safe only with its associated D1 mirror. If an isolated recovery environment restores an older D1 snapshot with a newer journal, clear the journal's `mirror_state` checkpoint in that isolated environment before replay. Never restore an older database over live claims. Reconcile all post-backup deletion/moderation tombstones before allowing any restored environment to serve traffic. Retain pinned catalog/scoring/rules versions and private recovery material with access controls. Current deletion tests do not constitute an audited backup-retention policy.

For a future release: export a consistent private journal snapshot and sequence, mirror to that watermark, capture D1/config/catalog versions, restore into an isolated namespace with no cron, no production origin fallback and no alerts, prove identities/replays/points/visibility after restart and rollback, and measure recovery time and lost-event count. This is a release gate, not a deferred safety exception.

Recommended later automation is laptop-independent private encrypted storage with envelope keys outside the backup, daily snapshots, seven daily plus four weekly retention sets, deletion reconciliation on restore, and a private failure alert. It needs a budget and access review; no bucket, secret, billing plan or notification was created in this run.
